## 2. Рівень 1

### 2.1 База та колекції
`library` з колекціями `books`, `authors`, `users`. На `books` одразу діє валідатор `$jsonSchema` (обов'язкові `title`, `author`, `publication_year`; типи `int`, `bool`, `array`). По **10 документів** у кожній колекції з різною структурою:
- `books`: масив `genres`, вкладений документ `publisher {name, city}`, масив документів `ratings [{user, score, date}]` (додається пізніше);
- `authors`: вкладений `birthplace {city|village, region}`, масиви `languages`, `awards`;
- `users`: вкладений `address {city, street}`, масив `borrowed_books`.

### 2.2 CRUD (`03_crud.js`)
Виконано: `insertOne`, `insertMany`; `find` з рівністю, `$gt`, `$or`, `$regex`, запитом по елементу масиву (`genres: "поезія"`) і по вкладеному полю (`"publisher.city"`), проєкцією, `sort`, `limit`; `updateOne` (`$set`, `$push`, `$inc`, `$unset`), `updateMany`, `replaceOne`; `deleteOne`, `deleteMany`. Приклад результату видалення:
```
deleteMany({temp:true, available:false}) → { acknowledged: true, deletedCount: 2 }
deleteOne({title:"Застарілий довідник"}) → { deletedCount: 0 }     // такої книги немає — це очікувано
```

### 2.3 Індекси та порівняння швидкості (`04_indexes.js`)
Створено три індекси на `books`: простий `{title:1}`, складений `{author:1, publication_year:-1}`, унікальний `{isbn:1}` (з `partialFilterExpression`, щоб документи без `isbn` не конфліктували між собою). Повторна вставка існуючого ISBN відхиляється (`E11000`, код 11000).

На 10 документах різниця непомітна (0 мс), тому додатково згенеровано **200 000 документів** (`books_perf`). Результати `explain("executionStats")`:

| Запит | Без індексу | З індексом |
|---|---|---|
| `author = "Іван Франко #2"` (100 рез.) | COLLSCAN, переглянуто **200 000** док. | IXSCAN `author_1`, переглянуто **100** |
| `isbn = "978-966-0123456"` | COLLSCAN, 200 000 док. | IXSCAN `isbn_1`, **1** док. |
| `author = … AND year ≥ 1900 ORDER BY year DESC` | SORT → COLLSCAN, 200 000 | IXSCAN `author_1_publication_year_-1`, **54**, без SORT |
| `year ≥ 2000 AND pages < 100` (1410 рез.) | COLLSCAN, 200 000 | IXSCAN `publication_year_1_pages_1`, 1410 |

Середній час запиту (30 запусків): **81 → 3 мс** (`author`), **94 → 2,5 мс** (`isbn`), **107 → 2,7 мс** (`author` + сортування). Ціна індексів: 12 МБ на диску (дані — 47 МБ) і повільніший запис.

> Індекс `{author:1}` окремо від `{author:1, publication_year:-1}` зайвий — складений індекс обслуговує запити і за префіксом `author`. У `books_perf` лишено обидва лише для наочності порівняння.

## 3. Рівень 2 (`05_level2.js`)

**Складні запити:** `$and` (після 1900, доступні, < 130 стор.), `$or` усередині `$and`, `$in`/`$nin`, `$regex` (`^К`, `/кохання/i`), `$all`, `$size`, `$elemMatch` (рейтинг ≥ 4 від `ivan_petrov`).

**Агрегації (pipeline):** кількість книг за жанрами (`$unwind → $group → $sort`) — найчастіший жанр «повість» (4), далі «реалізм» і «романтизм» (по 3); середня кількість сторінок за автором (найбільша — Панас Мирний, 384); книги за століттями (19 ст. — 7, 20 ст. — 3); топ користувачів за кількістю взятих книг (`olena_shevchuk` — 3); середній рейтинг; статистика за видавництвами.

**Складений індекс (правило ESR: Equality–Sort–Range).** Запит `genres="роман" AND available=true ORDER BY rating DESC LIMIT 20` на 200 000 документів:

| Індекс | План | Переглянуто документів |
|---|---|---|
| немає | SORT → COLLSCAN | 200 000 |
| `{genres:1}` | SORT → FETCH → IXSCAN | 40 000 (сортування в пам'яті) |
| `{genres:1, available:1, rating:-1}` | LIMIT → FETCH → IXSCAN | **20** |

**Текстовий пошук.** `createIndex({title:"text", description:"text"}, {default_language:"none"})`; `$text: "кохання Карпатах"` знаходить «Тіні забутих предків», «Intermezzo», «Маруся»; підтримано фразу в лапках, виключення `-слово`, сортування за `textScore`. Обмеження: без стемінгу `"Карпати"` ≠ `"Карпатах"` (пошук за «Карпати» дає порожній результат) — вирішується в п. 4.4.

**`$lookup`.** До `books` додано `author_id`; `books → authors` з `$unwind` та обчисленням віку автора на момент видання (наймолодший — Франко, «Каменярі», 22 роки); `authors → books` дає «LEFT JOIN»-подібний результат: три автори (Кобилянська, Вовчок, Нечуй-Левицький) мають 0 книг; `$lookup` з вкладеним `pipeline` + `$expr`.

**Представлення.** `available_books` (доступні книги, проєкція) і `books_with_authors` (на основі `$lookup`). View працює як колекція лише для читання: `db.available_books.find({publication_year:{$lt:1900}})`.

## 4. Рівень 3

### 4.1 Валідація JSON Schema (`06_validation.js`)
Через `collMod` задано розширену схему для `books` (довжина назви, діапазон року й сторінок, `pattern` для ISBN, `uniqueItems` для жанрів, вкладена схема `publisher` і `ratings`, оцінка 1–5) та для `users` (`enum` статусу, `pattern` email, `maxItems` для `borrowed_books`). `validationLevel: "strict"`, `validationAction: "error"`. Результат перевірки (усі некоректні операції відхилено з кодом **121**):

| Спроба | Результат |
|---|---|
| коректний документ | вставлено |
| `publication_year: 3000` | відхилено (`maximum`) |
| відсутнє поле `author` | відхилено (`required`) |
| `pages: "сто"` | відхилено (`bsonType`) |
| ISBN `123-ABC` | відхилено (`pattern`) |
| оцінка 7 | відхилено (`items`) |
| дублікати в `genres` | відхилено (`uniqueItems`) |
| порожня назва | відхилено (`minLength`) |
| статус користувача `banned` | відхилено (`enum`) |
| некоректний email | відхилено (`pattern`) |
| 6 взятих книг | відхилено (`maxItems`) |
| `updateOne` → `pages: -5` | відхилено (валідація працює і на оновлення) |

> Важливий нюанс: поле `bsonType: "int"` вимагає саме 32-бітне ціле. У `mongosh` цілі літерали зберігаються як `Int32`, але дані з інших драйверів (наприклад, Python `float`) будуть відхилені.

### 4.2 Геопросторові індекси та TTL (`07_geo_ttl.js`)
Колекція `libraries` (8 міст, GeoJSON `Point`, координати **навчальні, наближені**) з індексом `2dsphere`. Запити: `$near` (≤ 150 км від Луцька → Луцьк, Рівне, Ковель, Львів), `$geoNear` у pipeline з відстанями (Рівне — 67 км, Ковель — 67 км, Львів — 137 км, Київ — 369 км), `$geoWithin` з `$centerSphere` і `Polygon`. `explain`: `GEO_NEAR_2DSPHERE`.

TTL: `sessions` — `expireAfterSeconds: 3600`. Демонстрація на `sessions_ttl_demo` (5 с): одразу після вставки 2 документи, через 75 с — **0** (фонове видалення виконується раз на ~60 с, тому видалення не миттєве).

### 4.3 Версіонування документів (`08_versioning.js`)
Схема: поточний стан — у `books` (поле `version`), попередні стани — у `books_history {book_id, version, snapshot, changed_by, changed_at, comment}` з унікальним індексом `(book_id, version)`. Функція `updateBookVersioned` в **одній транзакції** зберігає знімок і змінює документ (`version+1`), з оптимістичним блокуванням (`_id + version` у фільтрі). `restoreBookVersion` відкочує до версії N, попередньо зберігши поточний стан (історія нічого не втрачає).

Приклад: три зміни «Кобзаря» (`version` 1→4), `diff` між версіями: `pages: 238 → 240`, `available: false → true`; `publisher.name: Дніпро → Наукова думка`. Оновлення зі застарілою версією дає `matchedCount = 0` (конфлікт). Після `restore` до v1: `pages: 238`, видавець «Дніпро», `version: 5`.
Альтернативи: Change Streams (запис змін у фоні), патерн «Document Versioning» з масивом `revisions` усередині документа (для невеликої історії).

### 4.4 Повнотекстовий пошук для української (`09_ukrainian_search.js`)
Вбудований текстовий індекс MongoDB не має української мови, а `default_language: "none"` не знає словоформ. Реалізовано власну нормалізацію: токенізація (Unicode, апострофи) + **евристичний стемер** по відмінкових закінченнях (`ння/нні/нням…`, `ами`, `ах`, `ою`, `ії`, `а/я/у/і/и/…`), стем ≥ 3 літер. Стеми зберігаються в полі `search_stems`, по ньому створено `text`-індекс; запит нормалізується тим самим стемером (`ukSearch(q)`).

| Запит | Нормалізовано | Знайдено |
|---|---|---|
| кохання / коханні | коха | Intermezzo, Маруся, Тіні забутих предків |
| Карпати (раніше — 0 результатів) | карпат | Тіні забутих предків |
| повісті | повіст | Intermezzo, Конотопська відьма, Маруся, Тіні забутих предків |
| поезії | поез | Кобзар, Каменярі |
| селянами | селян | Камінний хрест, Хіба ревуть воли… |
| Франка | франк | Каменярі, Захар Беркут |

**Обмеження:** це правила без словника — можливі помилки (чергування приголосних, «кохати» ≠ «кохання», дієслівні форми не обробляються). Для промислового використання: MongoDB Atlas Search з аналізатором `lucene.ukrainian` (потрібен Atlas / `mongot`), або зовнішній рушій (Elasticsearch + `hunspell`/`morfologik`). У цій роботі Atlas Search не перевірявся.

### 4.5 Реплікація (`11_replication.sh`)
Replica set `rs0` із трьох вузлів на одній машині (27017–27019).

| Крок | Результат |
|---|---|
| Стан | 27017 PRIMARY, 27018 і 27019 SECONDARY, відставання 0 с |
| Запис з `w:"majority"` | підтверджено |
| Читання зі вторинних (`readPreference: secondary`) | `books = 10` на обох |
| Запис на вторинний | `NotWritablePrimary` |
| `replSetStepDown` primary | новий PRIMARY — 27019 (автоматичні вибори), запис після перемикання успішний |
| Кінець | старий primary повернувся як SECONDARY; його знову зроблено PRIMARY (`replSetStepUp`) |

Це демонстрація на одній машині: вона показує механізм, але не дає реальної відмовостійкості (вузли ділять один диск/живлення). **Шардинг не налаштовувався** (критерій допускає «реплікація або шардинг»).

### 4.6 Резервне копіювання (`12_backup.sh`, `13_restore.sh`)
`mongodump --uri … --db library --gzip --archive=<файл>` з міткою часу, контрольною сумою SHA-256, ротацією (`KEEP_DAYS`, за замовчуванням 7), кодом повернення ≠ 0 за порожнього архіву; приклад cron-рядка — в заголовку скрипта. Архів `library_*.archive.gz` ≈ 6 КБ (без `books_perf`).

Перевірка відновлення (`13_restore.sh` → у БД `library_restore` через `--nsFrom/--nsTo`): кількість документів збігається — `books 10/10`, `authors 10/10`, `users 10/10`, `books_history 4/4`, `libraries 8/8`; **view** `available_books`, `books_with_authors` та індекси відновлено разом з колекціями. Контрольна сума перевіряється перед відновленням. Для узгодженого знімка на реплікованому наборі рекомендовано `--oplog` (для всього інстансу, не для окремої БД).

### 4.7 Порівняльний аналіз: реляційний і документний підхід
**Предметна область — бібліотека** (схема з методички: `authors`, `books`, `genres`, `book_genres`).

*Реляційна модель:* 4 таблиці, ключі й `JOIN` у запиті «книги з авторами та жанрами»; жанри — зв'язок M:N через `book_genres`. *Документна:* жанри — масив у книзі, автор — вбудований піддокумент (`author_id` для зв'язку з колекцією `authors`), видавець — вбудований.

**Виміри на MongoDB (`10_compare.js`, 200 000 книг, 2 000 авторів, по 100 книг на автора).** Одні й ті самі дані в двох моделях: автор вбудований у кожну книгу (`books_emb`) або лежить в окремій колекції (`books_ref` + `authors_ref`, `$lookup` ≈ JOIN):

| Операція | Вбудована модель | Посилання + `$lookup` |
|---|---|---|
| Розмір даних | 72 МБ | 29 МБ + 0,45 МБ |
| Прочитати 100 книг автора з даними автора | 3,5 мс | 4,7 мс |
| Прочитати лише книги автора | 2,0 мс | 3,4 мс |
| **Змінити ім'я автора** | **118 мс** (оновлення 100 документів) | **11 мс** (1 документ) |
| Аналітика по всіх 200 000 книгах за атрибутом автора | 756 мс | 4015 мс |
| Вставка 200 000 документів | 10,4 с | 8,5 с |

> Виміри зроблено на одній машині, у replica set із 3 вузлів із підтвердженням запису більшістю; час — усереднений і коливається від запуску до запуску (наприклад, у попередньому прогоні на одному вузлі зміна автора займала 5,8 мс проти 2,1 мс). Значущі тут **співвідношення**, а не абсолютні мілісекунди. PostgreSQL у цій роботі не розгорталася, тому порівняння з нею — якісне.

**Висновки.**
| Аспект | Реляційна (PostgreSQL) | Документна (MongoDB) |
|---|---|---|
| Моделювання | нормалізація, один факт — одне місце | денормалізація під патерни доступу; дублювання |
| Читання «книга + автор + жанри» | 3 `JOIN` | один `find` (вбудовано) або `$lookup` |
| Зміна довідкових даних | 1 рядок | кількість документів ∝ числу вбудованих копій (див. 118 мс vs 11 мс) |
| Аналітика/звіти з агрегатами за зв'язаними сутностями | сильна сторона (оптимізатор `JOIN`) | швидко лише коли потрібні поля вбудовано; `$lookup` у 5 разів повільніший у виміру |
| Схема | жорстка, `ALTER TABLE` | гнучка + опційна `$jsonSchema` |
| Цілісність | `FOREIGN KEY`, `CHECK` | немає FK; цілісність посилань — відповідальність застосунку |
| Транзакції | повні ACID | ACID-транзакції на replica set (використано у 4.3), але вони дорожчі, ніж у реляційних СУБД |
| Масштабування | переважно вертикальне, реплікація; шардинг — розширення | шардинг і реплікація вбудовані |

**Рекомендація для бібліотеки.** Автор змінюється рідко, а книги читаються часто, тому вбудовувати стабільні та невеликі дані (жанри, видавець) доцільно; для `authors` краще лишити окрему колекцію й посилання (дані автора ширші та змінюються самостійно), а у книзі зберігати `author_id` + «знімок» імені для швидкого відображення. Записи видачі книг, які ростуть необмежено, не слід вбудовувати в користувача (ліміт документа 16 МБ) — окрема колекція `loans`. Якщо головні задачі системи — облік видач, штрафи, фінансові звіти й складні зв'язки між багатьма сутностями, реляційна модель буде безпечнішою.

**Зв'язок з ЛР №4 («ТехноМарт», PostgreSQL).** Там замовлення розбито на `orders` + `order_items` (3НФ, ціна в `order_items.unit_price` як «знімок» на момент продажу). У MongoDB природний вигляд — один документ-замовлення з вбудованим масивом `items [{product_id, name, unit_price, quantity, discount}]`: замовлення читається одним запитом, а ціна на момент продажу зберігається самим дизайном. Каталог `products` залишається окремою колекцією, бо ціни й залишки змінюються. Саме так тут працює принцип «вбудовуємо те, що читається разом і не змінюється, посилаємось на те, що змінюється».

## 6. Відповіді на контрольні запитання (стисло)
1. **Реляційні vs документні.** Реляційні — таблиці з жорсткою схемою, нормалізація, `JOIN`, сильні ACID-гарантії: фінанси, облік, складні зв'язки. Документні — гнучка схема, вкладені структури, горизонтальне масштабування: каталоги, профілі, контент, події, дані з мінливою структурою.
2. **BSON.** Двійковий формат JSON-подібних документів: додаткові типи (`ObjectId`, `Date`, `Int32/Int64/Decimal128`, `BinData`), швидший розбір завдяки префіксам довжини, можливість обходу без повного розбору. Мінус — іноді більший розмір, ніж у JSON.
3. **Денормалізація.** Зберігання пов'язаних даних разом. Плюси: читання без `JOIN`. Мінуси: дублювання, дорожчі оновлення й ризик розсинхронізації (див. 118 мс vs 11 мс у п. 4.7).
4. **Pipeline.** Послідовність стадій, кожна приймає потік документів попередньої: `$match` (фільтр; ставити першим, щоб використати індекс), `$project`, `$unwind`, `$group`, `$sort`, `$limit/$skip`, `$lookup`.
5. **Індекси.** B-дерева, що замінюють перегляд колекції пошуком по ключу (200 000 → 1–100 переглянутих документів). Типи: одиночний, складений, унікальний, частковий (`partialFilterExpression`), multikey (по масивах), `text`, `2dsphere`, hashed, TTL, wildcard. Ціна — місце й повільніший запис.
6. **`updateOne/updateMany/replaceOne`.** Перші два змінюють окремі поля операторами (`$set`, `$inc`, …) в одному/усіх підходящих документах; `replaceOne` повністю замінює документ (крім `_id`), поля, яких немає в новому, втрачаються.
7. **Валідація схеми.** `validator: {$jsonSchema: …}` при `createCollection`/`collMod`; рівень `strict/moderate`, дія `error/warn`; перевіряється при вставці й оновленні (див. 4.1).
8. **Зв'язки.** Вбудовування (1:1, 1:few, дані читаються разом, швидко, але дублювання й ліміт 16 МБ) і посилання (`_id` + `$lookup`; нормалізовано, але потрібен додатковий запит/`$lookup`).
9. **Текстовий індекс.** Індекс по токенах (з урахуванням стоп-слів і стемінгу мови); запити `$text`, `textScore`; один на колекцію; для української — власна нормалізація або Atlas Search (див. 4.4).
10. **Масштабування.** Реплікація — копії даних на кількох вузлах (доступність, читання зі вторинних, автоматичний failover; показано в 4.5). Шардинг — розподіл даних за ключем шардингу між кластерами (`mongos` + config servers) для масштабування обсягу й запису; у роботі не налаштовувався.
